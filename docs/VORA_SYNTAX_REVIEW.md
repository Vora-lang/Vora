## 0. 一句话结论

Vora 的语法是「**JS 的形 + Python 的味 + Go/C 的碎片 + Rust 的 match**」的拼装体，**单条语法拿出来都能用，但组合起来有 4 处会静默改变语义的陷阱**，以及一串**学到一半才会撞上的能力断头路**。
最严重的问题不是"少了什么"，而是：**有几处你写对了意图，编译器却不报错、给你另一个意思。**

严重度分布：

| 级别 | 数量 | 性质 |
|---|---|---|
| **P0 静默错意** | 4 | 代码能跑、结果不对、无任何警告 |
| **P1 能力断头路 / 不对称** | 12 | 按直觉写就报错或静默降级 |
| **P2 一致性与可演进性** | 8 | 现在能忍，语言一长大就疼 |
| **P3 语法与实现/文档脱节** | 4 | 文档承诺的语法实际不存在 |

## 1. P0 —— 静默错意（最该先修）

### 1.1 没有语句终止符，且换行不敏感 → 跨行代码被静默吞并 【实测 A1 / A1b】

```vora
let a = 5
let b = a
-1
print(b)        // 实测输出 4，不是 5
```

```vora
func f(x) { return x * 10 }
let v = f
(3)
print(v)        // 实测输出 30 —— 它调用了 f(3)
```

`;` 完全可选，**换行也不承载任何语法意义**（`Vora` 把换行当普通空白）。于是"上一行能不能继续"完全由下一个 token 决定。

**为什么这是 P0**：主流语言都做了选择，Vora 是唯一"两头都不选"的：

| 语言 | 做法 | 后果 |
|---|---|---|
| C / C++ / Java | 强制 `;` | 无歧义，代价是打字 |
| Go | 词法 ASI（换行后遇特定 token 才插 `;`） | 上面两个例子都安全 |
| JS | 启发式 ASI | 有坑，但括号/运算符开头有明确规则兜底 |
| Python | 换行即终止，需 `\` 或括号续行 | 上面两个例子都安全 |

Vora 把 `;` 做成可选，却没有配套的 ASI 规则，**等价于把 C 的"必须写分号"和 Python 的"换行即语句结束"两条保护同时去掉了**。

**建议（三选一，越靠前越好）**：
1. **`;` 改为强制**，换行纯作空白（C 路线，最简单、工具链最友好）；
2. 保留可选 `;`，但**引入 Go 式词法 ASI**：当行尾 token 属于 `{标识符/字面量/)`/`]`/`}`/`return`/`break`/`continue`/`++`/`--`}` 且下一行开头不是可续接的中缀 token 时自动插 `;`；
3. 最低限度：当一行以 `- + ( [ .` 等**可续接 token 开头**且上一行已构成完整语句时，报 warning。

> 顺带：这直接决定了 formatter（你们已有 `vora fmt`）不能安全地做任何换行决策，因为**换行会改变程序含义**——这是格式化器的致命伤。

### 1.2 三元 `?:` 的优先级高于 `||`，与 C/C++/Java/JS 全部相反 【实测 T1 / C13】

```vora
print(true || false ? "A" : "B")      // 实测 "true"
print((true || false) ? "A" : "B")    // 实测 "A"
```

`src/parser/parser.cpp:1446` 的优先级表：

```
OR / ??        → 1
AND            → 2
QUESTION (?:)  → 2     ← 三元与 && 同级，且高于 ||
```

C/C++/Java/JS 中三元的优先级**低于** `||`，因此通用读法是 `(a || b) ? c : d`。Vora 反过来，读作 `a || (b ? c : d)`。

真实杀伤场景（条件判断里最常见）：

```vora
let ok = isAdmin || isOwner ? true : false     // 你以为在选布尔，实际拿回的是 isAdmin 的真值本身
```

**建议**：把 `QUESTION` 调到**低于 `OR`**（即 0 或单独设一级），并保持右结合。这是一行数字的修复，但必须先做——它已经在静默产生错误代码了。

---

### 1.3 命名参数的 2-token 前瞻吞掉了"赋值表达式作为实参" 【实测 T9 / T10】

```vora
func f(x) { return x }
let a = 1
print(f(a = 5))     // 实测报错：Unknown parameter name: a
```

`parser.cpp:1912` 的判定是：实参位置只要出现 `IDENTIFIER` 紧跟 `EQUAL`，**一律判为命名参数**。于是：

- `f(a = 5)` 若 `f` 有形参 `a` → 静默变成命名传参（**不是**你想要的"先赋值再传值"）；
- 若没有形参 `a` → 报 "Unknown parameter name"。
- **你永远无法把"赋值表达式的值"直接作为位置实参传递**，只能写成 `f((a = 5))`。

**各语言视角**：Python 靠"形参表里有这个名字"消歧（语义层），JS 根本没有命名参数所以赋值表达式永远合法（语义层）。Vora 在**语法层**用 2-token 前瞻抢走了这个形式，代价是永久失去该表达式形式。

**建议**：
- 方案 A：改用 `name: value`（Python/JS 对象风格）或 `name => value` 作为命名参数记号，把 `=` 还给赋值表达式；
- 方案 B：保留 `=`，但只在该标识符**确实是本函数形参名**时才当命名参数（需要编译器拿到被调用者签名，对动态语言不总是可行）；
- 方案 C（最小改动）：命名参数改用 `name := value`（Go 的短声明符号，视觉上不像 `==` 也不像 `=`）。

---

### 1.4 `import` 的绑定名从路径字符串派生，非法标识符静默变成减法表达式 【实测 C8 / C9】

```vora
import "./foo-bar"
print(foo-bar.V)
// 实测：Error: Undefined variable 'foo'
```

`foo-bar.V` 被解析成了 **`foo` 减 `bar.V`** —— 一个减法表达式，而不是"模块名不合法"的语法错误。

**为什么这是设计缺陷**：`import` 把**一个字符串字面量**当成**一个标识符声明**来用，这是让文法失去控制的典型做法。文件名里出现 `-`、`.`、数字开头、保留字，都会产生一个"看起来能写、实际是别的意思"的绑定。

**各语言视角**：
- Python：`import foo-bar` 直接非法，你得 `importlib` 或改文件名 —— **在语法层就拒绝**；
- Go：包名由文件内 `package xxx` 声明，与目录名解耦；
- JS：`import x from "..."` 由**调用方**显式命名。

**建议**：去掉"从路径派生绑定名"这条规则，强制二选一：

```vora
import "./foo-bar" as fb        // 显式别名（现已支持，实测 C9 通过）
from "./foo-bar" import V       // 具名导入（现已支持）
```

若确实要保留默认绑定，必须在**路径不是合法标识符时报错**，而不是静默产出一个非法绑定。

## 2. P1 —— 能力断头路与不对称（按直觉写就撞墙）

| # | 问题 | 证据 | 说明 |
|---|---|---|---|
| 2.1 | **`in` 不是表达式运算符** | 实测 T8：`print(1 in [1,2,3])` → 语法错误 | Python 程序员会写 `if (x in arr)`。该 token 只在 `for-in` 与推导式里出现（`parser.cpp:657/1701/1803`）。要么补成运算符，要么在错误信息里明确提示 |
| 2.2 | **`for (` 无条件走 C 风格 for** | 实测 T7：`for (x in [1,2,3])` → `Unexpected token: in` | 括号版 for-in 直接死。Go/Python 背景的人第一反应就是加括号。建议：消费 `(` 后先试探 `IDENTIFIER + in`，命中则走 for-in |
| 2.3 | **完全没有位运算符** | 实测 T12 `6 & 3` → 报错；T13 `~5` → 报错 | 一个带 C 风格 for、`defer`、`0x/0o/0b` 字面量、面向嵌入场景的语言，没有 `& \| ^ ~ << >>` 意味着**标志位、掩码、哈希、协议解析全部无法表达**。讽刺的是 `parser.h:693` 的优先级注释里还留着 `BITWISE_OR / BITWISE_XOR / BITWISE_AND` 三级 —— 说明曾计划过但没做完 |
| 2.4 | **match 的或模式 `\|` 根本不存在** | 实测 A7：`3 \| 4 => "small"` → `Unexpected character: '\|' (did you mean '\|\|'?)` | `USER_GUIDE.md:708` 白纸黑字写了或模式。词法层根本没有 `\|` 这个 token。要么补 `PIPE` token + 模式文法，要么删文档 |
| 2.5 | **没有一元加号** | 实测 B10：`+5` → `Unexpected token: +` | 有一元减号却没有一元加号，不对称。`5 + +3`、`+"42"` 全部写不出来 |
| 2.6 | **`**=` 缺失** | 实测 T18：`x **= 3` → 报错 | 有 `+= -= *= /= %=`，唯独没有幂赋值；而 `**` 本身是支持的。补全只需加一个 token |
| 2.7 | **`let` 必须初始化** | 实测 A9：`let x` → `Expected '=' after variable name` | 无法"先声明后赋值"。所有 C/Go/Java 背景的人都会撞：`let x; if (c) { x = 1 } else { x = 2 }` 写不出来，只能 `let x = null` 或三元。这是动态语言里**完全没必要**的限制 |
| 2.8 | **没有标签 break/continue** | 实测 A11：`outer: for ...` → `Unexpected token: :` | 嵌套循环只能靠布尔标志退出。Go/Java/JS 都有标签。既然提供了 C 风格 for 这种"容易写出嵌套循环"的构造，就该配套 |
| 2.9 | **`and`/`or` 有关键字，`not` 没有** | 实测 T5 通过 / T6 报错 | 关键字与符号双轨制本身可接受（Python 用词、JS 用符），但**双轨必须成对待齐**：`and`/`or` 有了，`not` 却没有，只能写 `!a`。要么补 `not`，要么删掉 `and`/`or` 只留 `&&`/`\|\|` |
| 2.10 | **字符串插值无法转义** | 实测 B5：`"\${x}"` → 输出 `\1`（反斜杠被原样保留，`${x}` 照样插值） | 没有 `\$` 转义。要输出字面 `${`，只能写 `"$" + "{x}"`。在**单引号字符串也插值**（实测 T19）的前提下，等于**无法写出字面 `${...}`**。这是硬缺口 |
| 2.11 | **对象字面量无简写，解构模式却有简写** | 实测 T14 `let x=1; {x}` → `Expected ':' after dict key`；实测 T15 `let {name, age} = ...` 正常 | 两种写法长得一模一样，文法支持却不同。用户从解构学到简写，转头写对象字面量就报错。要么都支持（推荐，2026 年的语言不该没有 shorthand），要么都不支持 |
| 2.12 | **rest 解构只在函数体内可用** | 实测 A18 顶层 `let [first, ...rest] = [...]` → `only supported inside functions`；实测 B1 放进函数内正常；实测 T16 对象 rest 同样受限 | `USER_GUIDE.md:581` 的顶层示例是错的。这种"看位置才生效"的限制对使用者完全不可预测，且错误信息不带任何补救提示 |

## 3. P2 —— 一致性与可演进性（现在能忍，长大就疼）

### 3.1 `Obj` 体内的 `func` 位置敏感，且无法声明局部辅助函数 【实测 T25 / A5 / B7】

```vora
Obj P() {
  func helper() { return "H" }   // 被当成"方法"提升，不是局部函数
  this.v = helper()              // 实测 RuntimeError: Undefined variable 'helper'
}
```

`parser.cpp:1275` 只按"是否在 Obj 体顶层"来区分方法与普通语句。结果：
- **类体里写不了任何私有辅助函数**；
- 唯一绕过方式是再套一层 `{}`（实测 A5 通过），这显然不是设计，是巧合；
- 对比：方法里嵌套函数正常（实测 B7）。

**建议**：引入显式修饰符（`func` = 局部函数，`method` / `this.func` = 实例方法，`this.func` = 静态方法），而不是让位置承载语义。

### 3.2 解构模式是 cover grammar（先按表达式解析再回溯转换）【源码】

`parser.cpp:2264` / `convertDictExprToBinding()`：先把 `{a, b}` 当 `DictExpr` 解析，再 walk AST 转成绑定模式。

这是 JS 箭头函数参数那套权宜之计。代价已经显现：
- **对象 rest（`{a, ...rest}`）至今缺失**（文档说 v0.23 计划，v0.27 仍无）—— 因为 `...rest` 在字典字面量里没有合法含义，cover grammar 无法承载；
- `let {1: a}`、`let {[k]: a}`（计算键）会被当模式接受，然后在语义层才炸；
- 错误信息说的是"dict key"而不是"pattern"，对使用者误导。

**建议**：把模式提升为独立的文法产生式（`pattern → arrayPattern | objectPattern | identifier`），与表达式解耦。

### 3.3 `:` 四重重载

同一个 `COLON` token 承担：字典键值分隔、三元 `else` 分支、类型标注（`:int`）、继承列表（`Obj Dog : Animal`）。
叠加 1.3 的命名参数问题，冒号/等号在 Vora 里的语义密度过高，对人和对解析器都不友好。

### 3.4 `for` 四重含义

C 风格 for、for-in、列表推导、字典推导，共用一个关键字，靠 `for (` 与 `for ... in` 的前缀区分。加上 2.2 的问题，这里是全语言最容易误用的路口。

### 3.5 `..` / `..=` 两个专用 token 只在一个地方可用 【实测 T17】

`let r = 1..5` → `Unexpected token: ..`。两个专用 token 只在 match 模式里有效，**没有 range 表达式、没有切片**。
（好消息：词法层处理正确，`number()` 只在 `.` 后紧跟数字时才吃小数点，`1..5` 不会被切成 `1.` + `.5`。）

**建议**：要么补 range/切片表达式（与既有 token 复用，性价比高），要么承认这是 match 专用记号并改名。

### 3.6 `Obj` 大写，其余 32 个关键字全小写

`Obj` 是唯一首字母大写的关键字。在一个把 `null`/`true`/`false` 都做成小写关键字的语言里，这个例外没有收益，只会让人反复怀疑"是不是我拼错了"。

### 3.7 `defer` 与 `finally` 两套清理机制并存

Go 带进来了 `defer`，Java/JS 带进来了 `finally`。功能重叠，且**在异常路径上二者执行顺序**需要明确定义（文档 v0.25/v0.26 分两版才补完 defer 与 throw 的交互）。对使用者是"我该用哪个"的额外决策成本。

### 3.8 `match` 无匹配臂时静默返回 `null` 【实测 A3b】

```vora
let r = match 99 { 1 => "one", 2 => "two" }   // 实测 r = null
```

没有穷尽性检查，没有告警，`null` 会一路传播到很远的地方才炸。要么要求穷尽（有 `_` 或类型覆盖），要么无匹配时报错。

### 3.9 `as` 关键字注释声称可用于"类型转换"，实际只有 import 别名一种用途 【源码】

`token.h`：`AS, ///< 'as' Import alias, type cast`。全 `parser.cpp` 只在 `2430` 行（import 别名）用到。要么补 cast 语法，要么修注释。

### 3.10 文档声称 `if`/`while` 条件括号可选，实际强制 【实测 B8 / C1】

`USER_GUIDE.md:247` 写"条件周围括号可选"，实测 `if x > 10 {` → `Expected '(' after if`，`while i < 3 {` → `Expected '(' after while`。
（这是文档错，不是语法错 —— 但使用者按文档写会撞墙。既然做了 C 风格 for 和 defer，允许无括号条件其实是 Go 用户最期待的那口糖。）

## 5. 修复优先级建议

## 6. 总体判断

Vora 的语法**完成度其实不低**：33 个关键字覆盖了 async/await、生成器、多继承 C3 MRO、模式匹配、推导式、解构、可选链、defer —— 这是一份很有野心的清单，且大部分**真的能跑**。

问题在于**它是"按特性清单横向堆"长出来的，而不是按一套自洽的核心文法纵向长出来的**，于是留下了三类伤疤：

1. **优先级表是抄来的，没有重新推演** → 三元与 `||` 倒置（1.2）；
2. **新特性用"位置 + 前瞻"硬塞进旧文法** → 命名参数（1.3）、Obj 体 `func`（3.1）、解构 cover grammar（3.2）；
3. **特性加了一半** → 无位运算却有 C 风格 for、`**` 有 `**=` 没有、`and/or` 有 `not` 没有、简写解构有简写字面量没有。

对使用者的净效果是：**"能写的比我以为的少，写错了也不告诉我"**。这比单纯"功能少"更伤信任。

按第 5 节的前两批修完（约 10 项），Vora 的语法会从"能用的拼装体"跨到"可以放心依赖的语言"。

## 附录：顺带发现的非语法问题（不在本次评审范围，但值得单独修）

> 这些不是语法设计问题，故放在最后，供参考。

1. **当前 HEAD 在 MinGW/GCC 下编译不过**：`src/ast/binding_pattern.h:42` 缺 `#include <cstdint>`（`uint8_t` 未定义）、`src/gc/gc_heap.cpp:123` 缺 `#include <algorithm>`（`std::remove_if` 未找到）。MSVC 下可能因为间接包含侥幸通过，属隐式依赖。本次评审为拿到可执行的 v0.27，是用 `-include cstdint -include algorithm ...` 强制注入绕过，**未修改任何源码**。
2. **`defer` 的参数在延迟执行时求值，而非注册时** 【实测 A16】：`defer print(x)` 中 `x` 在 return 时才求值（打印 99 而非 1）。Go 相反，在 `defer` 语句处即求值。文档称"类似 Go 的 defer"，此处行为与 Go 不同。
3. **字典访问不存在的 key 抛运行时异常** 【实测 B11】：`d.b`（dict 无此 key）→ `RuntimeError: Unknown dict key or method: b`，而不是返回 `null`。这意味着 `?.` 不是"可选"而是**访问 dict 的唯一安全写法**，且无法区分"键不存在"与"真错误"。
4. **`Vora` 仓库的推送尚未完成**：上一轮 `Vora-LSP` 已推送成功（`098d129`），但 `Vora` 仓库被远端拒绝——远端 `main` 领先本地 4 个提交（`ed722dd` 等，含 VM 内联属性缓存、chunk string_view、解构默认值等），本地提交 `9698b9b` 尚未推送。需要 rebase 后再推。
