# 大整数（方案 a：混合表示）设计

> 状态：**设计阶段，未实现**
> 触发问题：整数被静默夹取到 ±2⁴⁵，与文档承诺的 int64 不符（见 §1）
> 目标：让 Vora 能像 Python 3 一样处理任意大的整数，同时保住 NaN-boxing 的小整数快路径
> 备注：这是**语义级决定**，应写入 v1.0 契约；本文只做设计，不含实现

---

## 1. 问题（已实测确证）

`src/runtime/value.h` 的实际布局：

```
[62:52] = 0x7FF (NaN 指数)   [51] = QNAN
[50]    = VORA_TAG_BIT       [49:46] = 4 位类型标签（16 槽）
[45:0]  = 载荷（46 位 —— 指针或立即数）
```

而 `value.h:134/158` 明确写着整数按 **int47 夹取**：

```cpp
/// Integers outside [-35,184,372,088,832 .. 35,184,372,088,831] are clamped
/// @brief Construct an Int Value with int47-range clamping.
```

实测（当前 HEAD）：

| 输入 | 实测输出 | |
|---|---|---|
| `2^44` | `17592186044416` | ✅ 范围内 |
| `2^45` | `35184372088831` | ❌ 夹到上界 2⁴⁵−1 |
| `2^60` / `INT64_MAX` | `35184372088831` | ❌ 同样夹取 |
| `0x1000000000000`（2⁴⁸） | `35184372088831` | ❌ 十六进制同样中招 |
| `35184372088831 == 1152921504606846977` | `true` | ❌ 证明是存储阶段夹取 |

问题性质：**静默错值**——超出范围不报错、只给错的数。违反设计原则第 7 条（不可静默）。而 README / USER_GUIDE 均宣称「**Int64** 64 位有符号整数」。

**测试盲区**：411 单测 / 93 脚本 / 58 示例全绿，因为没有任何用例触及 ≥2⁴⁵ 的整数。位运算测试里 `(1 << 63) < 0` 之所以通过，是因为夹取后仍为负——又一次侥幸通过。

---

## 2. 为什么不能靠「加宽立即数」解决

立即数可用位数 = 64 − 13（NaN/标记位）= 51，其中类型标签占 4 位 → 载荷 46 位。现在把其中 1 位当符号用，得到 47 位有符号区间（±2⁴⁵）。

要显著加宽必须**减少标签位数**，而标签已用满 16 槽（含指针、字符串、数组、字典、函数、类、实例、Task 等），且 `VORA_TAG_BIT`（第 50 位）承担「与硬件 NaN 区分」的关键职责。**结论：8 字节 NaN-boxing 内无法再挤出足够位数**。要更大的整数，必须离开立即数表示。

---

## 3. 选定方案 (a)：混合表示

**小幅整数走内联（现状），超范围整数走堆上装箱。**

- 内联：`|v| ≤ 2⁴⁵−1` → 仍是现在的 int47 立即数，**快路径完全不变**（这是保住 NaN-boxing 收益的关键）。
- 装箱：超出该范围 → 新的堆对象 `GcBigInt`，`Value` 用一个新的类型标签指向它。

### 3.1 表示

在现有 4 位标签中占用一个空闲槽：

```cpp
enum class ValueTag : uint8_t {
    // ... 现有标签 ...
    BigInt,     ///< 载荷是指向 GcBigInt 的指针（超出 int47 立即数范围）
};
```

新的堆类型（沿现有 GC 对象约定）：

```cpp
class GcBigInt : public GcObject {
public:
    /// 小端 32/64 位 limb；不变量：高位 limb 非零、零值不入堆
    std::vector<uint64_t> limbs;
    bool negative = false;
    // 注：也可用单一 i128/符号+幅值，若先只支持到 2^63 之外的常见范围
};
```

**不变量**（必须在构造处断言，便于定位）：
1. 任何可被内联表示的整数**不得**装箱（否则相等判定与哈希会分裂）。
2. 零、以及所有内联范围内的值一律走内联。

### 3.2 `asInt()` 语义改为「可能丢失」

这是本方案**最需要警惕的地方**，也是与方案 (b)/(c) 的最大区别：

```cpp
int64_t Value::asInt() const;   // 对 BigInt 无法返回精确值
```

现状：`asInt()` 是无条件、无损的访问器（因为所有整数都能内联）。装箱后**它不再能对所有整数无损**。因此：

- `asInt()` 对 BigInt 的行为必须显式定义，三选一：**断言失败**（把问题暴露在开发期）／**抛出可捕获的运行时错误**／**返回截断值**（最危险，等于把静默错值从夹取搬到访问器）。
- 我建议：**断言 + 在 Release 下抛运行时错误**，绝不返回截断值；并把它作为审计清单的核心。
- 新增 `bool fitsInt64() const`（或 `toInt64Exact(int64_t& out)`）供需要精确值的调用点使用。

**审计清单（实现前必须逐项定案）**：所有 `asInt()` 调用点按类别梳理，至少覆盖：
- VM 算术/比较/位运算（`vm.cpp` 中的 `OP_*_NN`、`OP_ADD` 等）
- 编译期常量折叠（`compiler_expr.cpp`，含 `**`、`%` 的溢出守卫）
- 打印与字符串化（`toString` / `print`）
- 字典与 Set 的键哈希、相等（`value_ops.cpp`）
- 数组下标、`range()`、切片
- LSP / DAP / 嵌入 API / REPL

## 4. 算术语义（必须逐条定案）

| 情形 | 规则 |
|---|---|
| 内联 ⊗ 内联，结果在范围内 | 内联 int（现状不变，快路径） |
| 内联 ⊗ 内联，结果超出范围 | **自动装箱为 BigInt**（不夹取、不报错——这正是「像 Python」的含义） |
| 任一侧是 BigInt | 走 BigInt 算术；结果若落回范围，**降级回内联**（保证不变量 1） |
| int ⊗ float | float（现状）；BigInt ⊗ float → 转 double（可能丢精度，**需明示**是否允许；建议允许但文档写明） |
| BigInt ⊗ BigInt | 精确 BigInt 算术；`/` 的取舍见下 |
| `**` | 现为 float 且已文档化；建议**保持**（不引入 bigint 幂，避免与既有契约冲突） |
| `%` / `/` | `%` 建议 BigInt 精确取模；`/` 现为 float（`5/2 == 2.5`），BigInt `/` 建议同样返回 float 或 BigInt 截断——**需你定案**，这是最容易埋错的地方 |
| 位运算 `& \| ^ ~ << >>` | 现为 int64。BigInt 版需定义为二补码无限精度语义（Python 风格）或**明确拒绝 BigInt 参与位运算**——建议后者先行，降低首版风险 |
| 溢出 | **不再有静默溢出**：要么装箱，要么对明确超出的情形报错 |

**字面量**：`123456789012345678901234567890` 这类十进制字面量应解析为 BigInt（词法/解析层的整数字面量路径现在是 `std::stoll` + 溢出回退 `std::stod`——后者会丢精度，必须改为「溢出则构造 BigInt」）。十六/八/二进制同理（现在走 `std::stoull`，超 64 位即失败）。

## 5. GC 集成

- `GcBigInt` 继承 `GcObject`，由 `GcHeap` 分配，参与标记-清除（含分代 GC 的 minor/major 与写屏障）。
- 装入 `dict`/`Set` 键、数组元素时不需特殊处理（沿用现有 `GcPtr` 约定）。
- **注意**：装箱/降级会产生临时对象，热路径（如循环内的 `n += 1`）**不应**因装箱而变慢——不变量 1（范围内一律内联）就是为此。需在 `tests/bench/` 加回归基线，确认内联路径无性能变化。

## 6. 相等、哈希与键身份

- BigInt 与内联 int 在**数值相等**时必须相等（`2^45` 与 `2^45` 走过不同表示的两种构造不应产生不同键）。
- 哈希必须按**数值**归一化，而不能按表示，否则 `{2^45: 1}` 与用内联值构造的同一数值会分裂成两个键。
- 与 float 的相等沿用现有按值比较规则（`42 == 42.0` → true）。
- **测试**：同一数值的多种构造路径（字面量、算术结果、解析结果、装箱-降级往返）必须互相可查。

## 7. 嵌入 ABI（`vora.hpp`）——冻结前必须定案

这是**唯一不可事后补救**的部分。当前嵌入 API 有 `getGlobal()` / `setGlobal()` 等，暴露 `Value` 或 int64。装箱后：

- `asInt()` 对 BigInt 的行为（见 §3.2）会成为**公开契约**。
- 需要决定：是否暴露 `isBigInt()` / `asBigInt()` / `toString()` 的稳定接口？嵌入方如何安全地取任意精度整数？
- 一旦 v1.0 冻结，这里不能再改，**建议先定接口再实现**。

## 8. 错误策略（非静默）

- 字面量超出可表示范围（例如超出实现允许的最大 limb 数）→ **编译期错误**。
- 运行时不引入新的静默行为：不再夹取。
- 明确不支持的情形（如 BigInt 参与位运算的首版）→ **可捕获的运行时错误**，而不是近似值。

## 9. 测试计划

- 边界：`±(2^45−1)`、`±2^45`、`2^53`、`±2^63`、`2^64`、`INT64_MAX/MIN` 的字面量与算术结果
- 进制：同一边界的 hex / oct / bin 字面量
- 往返：装箱 → 降级 → 再装箱；`asInt` 在不该被调用处确实报错
- 相等/哈希：同一数值的不同构造路径互查（作为 dict 键、Set 成员）
- 混合：BigInt 与 int/float 的四则、比较；`%` 与 `/` 的定案语义
- 回归：**现有全部 411 单测 / 93 脚本 / 58 示例不变绿即视为失败**（内联路径必须零变化）
- 性能：`tests/bench/` 基线，确认内联快路径无回归
- 嵌入：`examples/embed/` 覆盖 BigInt 的取用与错误路径

## 10. 非目标

不定长小数/`decimal`、有理数、`float128`、BigInt 的 `**`、BigInt 位运算（首版）。也不改变 `/` 与 `**` 现有的 float 语义（除非 §4 的定案要求）。

## 11. 分阶段实施（每步一个提交，可独立验证）

1. **止血（小、立即可做）**：把「超范围整数静默夹取」改为**显式报错**（字面量编译期错误、运行时运算溢出报错）。不改表示、不破坏 8 字节设计，只是让错误可见。**可先单独交付。**
2. 引入 `GcBigInt` + 新标签 + 不变量断言；`Value(int64_t)` 超范围时**暂时**仍报错（保证表示已就位但行为未放开）。
3. 整数算术的装箱/降级路径（四则、比较）+ 常量折叠对齐。
4. 字面量解析（十进制/十六/八/二进制）支持任意长度。
5. 相等/哈希归一化 + dict/Set 键测试。
6. 打印/字符串化、LSP/DAP、嵌入 API。
7. 性能基线与内联快路径零回归确认。

## 12. 风险

| 风险 | 级别 | 缓解 |
|---|---|---|
| `asInt()` 被某个热路径无条件调用，装箱后行为未定义 | **高** | §3.2 的审计清单必须先做完并落成测试；绝不返回截断值 |
| 相等/哈希未按数值归一化，导致 dict/Set 键分裂 | **高** | §6 的多种构造路径互查测试，必须在实现早期就写 |
| 内联快路径被拖慢（装箱检查进热循环） | 中 | 不变量 1 + bench 基线；装箱判断保持在分支可预测的形态 |
| 嵌入 ABI 事后无法收敛 | **高** | §7 先定接口再实现；v1.0 冻结前完成 |
| 与 `/`、`**` 既有 float 契约冲突 | 中 | §4 逐条定案并写进 EBNF/USER_GUIDE；不改已文档化行为 |
| 首版范围蔓延（位运算、幂、混合精度） | 中 | §10 非目标 + §11 分阶段；先只做精确四则与比较 |

---

## 13. 需要你先拍板的四件事

1. **`/` 与 `%` 的 BigInt 语义**（§4）：`/` 返回 float 还是 BigInt 截断？`%` 是否精确取模？
2. **BigInt 是否允许参与位运算**（首版建议拒绝）。
3. **`asInt()` 对 BigInt 的行为**（§3.2）：断言 + Release 抛错（我建议）／总是抛错／其他。
4. **嵌入 ABI 接口**（§7）：是否暴露 `isBigInt`/`asBigInt`，或统一走 `toString`。

这四条定了，实施路径就没有别的分叉了。
